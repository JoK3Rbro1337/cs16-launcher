Never run destructive or corruption test scenarios against the real CS 1.6 install. Use a temporary sandbox game directory for all sync/switching/corruption tests. The real install may only be touched by the normal user-facing sync flow.

CDP monkeypatching of `window.launcher` (contextBridge objects) NEVER works — they are frozen; the patch fails silently and real IPC fires. This has now caused two incidents (M8, M10d). For UI verification of sync/launch flows, use an isolated harness with a mock bridge, never the live app against the real install.

Before pushing any release tag (`vX.Y.Z`), always validate the electron-builder config locally first: `npx electron-builder --linux --publish never`. v0.3.0's first tag attempt failed at CI's config-validation step — before any real build ran — on an issue this local command catches in seconds instead of burning a CI run. **Gotcha:** `publish.draft` (boolean) doesn't exist in electron-builder's current `GithubOptions` schema (`additionalProperties: false` rejects it outright, which cascades into the whole `publish` block failing `anyOf` validation) — the replacement is `publish.releaseType: draft | prerelease | release` (default `draft`; use `release` for an immediately-live, undrafted release). Don't reintroduce `draft` as a config key.

`content/` (and the root `manifest.json` generated from it) is a working directory whose contents get published **verbatim** to GitHub Releases via `scripts/generate-manifest.mjs` + `gh release upload` — anything placed under `content/slots/<slot>/<variant>/` becomes a public, downloadable asset the moment that release is pushed. Never copy a personal file (your own `config.cfg`, real name/nickname, anything not meant for distribution) into `content/` for any reason, including as scanner/test fixture data — use the local-variant mechanism instead (`electron/modules/local-config-variant.ts`'s "My Config" snapshot, stored under Electron's userData dir, never published) or a throwaway fixture file outside `content/` entirely (e.g. in a scratch dir, or inline in a verify script). `content/` and `manifest.json` are gitignored, so `git status` looking clean is not a safety signal here — the real check is "would this be an asset on the next `gh release upload`?" **Incident (2026-08, M12.5 follow-up):** a personal `config.cfg` (real Steam display name) was copied into `content/slots/config/my-config/` as ad-hoc fixture data, got included in a `generate-manifest.mjs` run, and was live as a public release asset (plus selectable in `manifest.json`) on `content-v2` for a period before being caught and removed (asset + manifest entry deleted and manifest re-uploaded, verified clean). `generate-manifest.mjs` now hard-fails if it finds a slot variant with id `my-config` (collides with `LOCAL_VARIANT_ID`) — see its `RESERVED_LOCAL_VARIANT_ID` check — but that only catches the one known collision, not personal data under any other name.

Known conventions:
- Sandbox-only for destructive tests (see rule above).
- Stock CS 1.6 paths are flat, e.g. `cstrike/models/v_deagle.mdl` — there is no `models/weapons/` subfolder in the vanilla depot.
- The config mechanism (M9) execs variant/feature `.cfg` files via an identical managed block written to both `cstrike/autoexec.cfg` and `cstrike/userconfig.cfg`, delimited by BEGIN/END markers; everything outside the block is left untouched.
- **Gotcha (M9 follow-up, real-world finding):** `autoexec.cfg` auto-execution is unreliable on modern Steam GoldSrc builds — some builds only exec it when `+exec autoexec.cfg` is present in the game's Steam Launch Options; never assume it fires on its own. `userconfig.cfg` is the reliable zero-setup path (exec'd via the `exec userconfig.cfg` line Valve's own stock `config.cfg` already ends with), so it's now the primary managed-block target, with `autoexec.cfg` kept as a redundant fallback. See `electron/modules/steam-launch-options.ts` for the read-only Launch Options check. **Confirmed on the real install (2026-07-26):** config variants apply correctly via `userconfig.cfg` with no `+exec autoexec.cfg` launch option set — the zero-setup path fires automatically on this build, as expected.
- **Standing rule (incident, 2026-08): `userconfig.cfg` and `autoexec.cfg` must stay leaves of the exec graph.** Never write a managed exec of a profile/variant config into either that itself (directly or transitively) execs back into `userconfig.cfg`/`autoexec.cfg` — that closes the graph into a cycle by construction, and **GoldSrc has no recursion guard**: it hangs rather than erroring. **Symptom signature — recognize this immediately, don't chase the graphics stack:** black screen at launch (never reaches the first rendered frame), the process pegged at 100% CPU (R state), and a completely unresponsive game window (can't move or close it). A live incident cost a week chasing Mesa/kernel/Wayland regressions before a gdb backtrace on the hung `hl_linux` process revealed 3000+ stack frames of `Cmd_ExecuteStringWithPrivilegeCheck → Cbuf_Execute → Cmd_Exec_f → ...` repeating — i.e. infinite mutual `exec` recursion, not a graphics bug. Root cause: any config a manifest variant ships can legitimately end with GoldSrc's standard engine-written trailer (`exec controller.cfg` / `exec userconfig.cfg` — Valve's own client appends this whenever it saves settings), and the launcher was writing `exec <that variant>.cfg` into `userconfig.cfg`'s managed block, closing `variant.cfg → userconfig.cfg → variant.cfg → ...`. Fix (`electron/modules/content-sync.ts`): `syncManagedExecTargets` now calls `findManagedExecCycle` *before* writing anything to either managed target — it walks the exec graph that would exist immediately after the write (both managed targets treated as pointing at the incoming `execPaths`, each further file's real on-disk `exec` statements followed recursively via `config-scanner.ts`'s `extractExecTargets`, classic DFS + recursion-stack cycle detection so it catches any cycle in the reachable graph, not just a direct back-reference) and throws `ManagedExecCycleError` — a clear, UI-surfaced error — if one would result; neither target is touched (existing content, including a player's own hand-edits outside the BEGIN/END markers, is left byte-for-byte intact). An unreadable/unresolvable exec target is treated as a dead end (false negative possible, never a false positive — never blocks a write that's actually safe). See `scripts/verify-content-sync.mts` for the regression coverage (direct cycle, transitive cycle through an intermediate file, self-cycle, safe writes still succeed, missing-file dead end, and the exact "workaround fixed upstream, next sync recovers cleanly" scenario). This is deliberately *not* caught by `config-scanner.ts`'s M12.5 rules — its `exec-outside-cstrike` rule only checks path traversal, and a plain `exec userconfig.cfg` is completely normal/expected in a real `config.cfg`, so it scores 100/clean while still being capable of this hang; cycle detection lives in the write path, not the scanner.
- **Gotcha (M12a, real-world finding):** `qconsole.log` (GoldSrc's `-condebug` output) lands at the game install **root** (`<gamePath>/qconsole.log`), not inside `cstrike/` — confirmed against a live install; a stock GoldSrc client also concatenates some prints (chat/kill-feed) with no newline between them, so log parsing must be regex-over-text, never line-anchored. `-condebug` is a hard requirement (unlike `+exec autoexec.cfg` above) — without it the engine never writes the file at all. See `electron/modules/session-watcher.ts`.
- OS process-list detection (`electron/modules/game-process.ts`, built for M12a) checks for `hl_linux` (native Linux client) / `hl.exe` (Windows/Proton) by name only — read-only, zero process/memory interaction. M15's crosshair overlay will reuse this same module to gate its own visibility.
- **Gotcha (M12a, live-use finding):** a "Create Game" listen server connects to `127.0.0.1`, which briefly showed up as "last server" on Home. Loopback (127.0.0.0/8) is filtered out of session tracking entirely; private LAN (10/8, 172.16/12, 192.168/16) is still tracked into the rolling history but never overrides a public server as the persisted/emitted "last server" — see `classifyAddress` in `session-watcher.ts`.
- **Gotcha (M12a, live-use finding):** `checkLaunchOptions()`'s parsing was verified correct against a real `localconfig.vdf` (including a genuine `-condebug` entry) — a live false-negative report traced most plausibly to Steam not flushing `localconfig.vdf` to disk instantly after a Launch Options edit, not a parsing bug. `CondebugNotice`/`LaunchOptionsNotice` re-check periodically (every 30s) rather than once on mount, so a stale read self-corrects.
- **Gotcha (server sources, live-use finding, 2026-07):** BattleMetrics' public servers API now returns 403 for every unauthenticated request ("Access denied. A subscription is required to use the API.") — confirmed directly against the live endpoint with multiple User-Agents, so it's a real policy change, not a User-Agent/IP block, and there's no free-tier workaround. The BattleMetrics source now defaults to OFF (`src/lib/serverSources.ts`) and surfaces its own `detail` message instead of a raw HTTP code when a user does enable it. All server-source failures degrade gracefully: favorites are merged into the query seed unconditionally regardless of source outcomes, per-source failures are shown in plain language on the Servers page (not just a raw status code), and one source failing never blocks the others or empties the browser on its own.
- **Gotcha (master server discovery, live-use finding, 2026-07):** `hl2master.steampowered.com` is a CNAME to `hl2master.discovery.steamserver.net`, which currently has no A/AAAA record at all — confirmed against multiple resolvers (system default, 8.8.8.8 directly via `dig`) with the CLI sandbox's own network restrictions explicitly lifted, on the user's actual machine, so this is a real Valve-infrastructure outage, not a local/sandbox artifact. The documented fallback IP `208.64.200.65:27015` doesn't answer the master protocol either (times out) and doesn't answer ICMP. Both hosts are still tried every refresh (cheap insurance if Valve fixes it later) but `MASTER_QUERY_TIMEOUT_MS` was cut from 3000ms to 1500ms since waiting the old duration on two now-dead hosts was pure tax on every refresh. Failure reason is surfaced (`QueryServersResult.masterError`) and shown plainly in both the Servers page funnel area and Settings' new "Master server discovery" status row, rather than a silent zero. Automated discovery beyond favorites/subscriptions now effectively depends on the default curated subscription (see Roadmap M11.3) since both BattleMetrics and master are currently non-functional.
- **Decision (server discovery, 2026-08):** the Steam Web API (`IGameServersService/GetServerList`) was evaluated as a master-server replacement and explicitly dropped by the user before any implementation — requiring a personal API key was judged too high a barrier for this audience, and GoldSrc/appid 10 support was never confirmed working in 2026 anyway. Discovery is instead built entirely on sources the launcher fully controls: the default curated subscription (M11.3), the self-growing known-servers pool, and the opt-in neighborhood scan (both below).
- **Self-growing discovery (M11.3 follow-up, done):** `electron/modules/known-servers.ts` persists a local pool of servers the player has actually connected to, fed from `session-watcher.ts`'s `handleConnect` — only public addresses whose own A2S query already succeeded are recorded (loopback/private-LAN and non-responsive connects never enter the pool). Merged into every refresh's seed alongside favorites, same unconditional-merge treatment (a source failing can't remove it). Entries are pruned once they haven't answered A2S within `retentionDays` (default 30, configurable in Settings) — pruning happens off real refresh results (the pool is queried in full every refresh), not a separate tracked counter. `electron/modules/neighborhood-scan.ts` is a second, **opt-in, off-by-default** source: probes the /24 around addresses in favorites + the known-servers pool only (never subscription/master/BattleMetrics addresses) on ports 27015–27020, using the same `queryServer` A2S call every other source's addresses get, capped at `MAX_NEIGHBORHOOD_PROBES` (200) per refresh with candidates shuffled before truncating so repeated refreshes explore different parts of a large /24; only addresses that actually answer are ever returned to the caller. Both surfaced in Settings' Server Sources section with the same address-count/last-check status pattern as every other source.
- **Gotcha (M12, Wayland notification-activation, 2026-08):** clicking a background-notification (M12) did nothing on KDE/KWin under Wayland — no window focus, no drawer. Root cause confirmed by inspecting the actual electron-builder AppImage output (`npx electron-builder --linux --publish never`, then `--appimage-extract` and `cat *.desktop`): the app had no `desktopName` set anywhere, so the generated `.desktop` file's `StartupWMClass` fell back to `productName` (`"1.6X Launcher"` — spaces, not a valid WM class) while Electron's own runtime app_id was whatever Chromium infers on its own; the two never matched, so KWin's xdg-activation had nothing to associate the activation request with and correctly refused to raise a window it couldn't identify. This is expected Wayland behavior (self-initiated activation without a matching, registered app_id is rejected by design), not a KWin bug and not something a retry/timing fix can work around. Fix: `desktopName: "com.cs16launcher.app.desktop"` added to `package.json`, `linux.syncDesktopName: true` added to `electron-builder.yml` (makes the installed `.desktop` filename and its `StartupWMClass` both derive from that same value), and `app.setDesktopName(...)` called in `electron/main.ts` before `app.whenReady()` (Linux-only) so the value is also correct in dev/unpackaged runs, not just packaged ones. Re-extracting the AppImage after the fix confirms `StartupWMClass=com.cs16launcher.app` matching the runtime app_id exactly. Even with a matching app_id, `window.focus()` from our own process is still just a *request* a compositor may ignore — `electron/main.ts`'s `focusOrFlagWindow` always applies the resulting state change (selects the server / opens its drawer) regardless of whether the window actually got raised, and falls back to `flashFrame` (taskbar/urgency hint) when focus didn't visibly take, so the user always gets *some* cue instead of nothing. Electron's Notification `actions` (native button row, e.g. a "Connect" button that bypasses window-raising entirely since `steam://connect` doesn't need focus) is darwin/win32 only per Electron's own typings — added anyway for those platforms, but it is not and cannot be the fix for Linux. See `electron/modules/notification-poller.ts` and `electron/main.ts`.
  - **Follow-up, real-world test (2026-08):** the `StartupWMClass`/app_id fix above was necessary but not sufficient — live-tested against the actual built AppImage: notification click did nothing at all (no focus, no `flashFrame` taskbar highlight either), and `~/.local/share/applications` had zero entry for us. Root cause: an AppImage runs completely unintegrated by default — nothing is ever installed into `~/.local/share/applications`, so KWin's xdg-activation has no registered desktop entry to check the running window's app_id against in the first place, regardless of how correct that app_id is. Fix: `electron/modules/linux-desktop-integration.ts`, an **opt-in, never-automatic** feature — writes a `.desktop` file to `~/.local/share/applications/com.cs16launcher.app.desktop` (`Exec` pointing at `process.env.APPIMAGE`, the AppImage runtime's own env var for its absolute path — only offered when that's set, i.e. never in a `npm run dev` run) plus a copy of the bundled icon referenced by absolute path (no icon-theme cache dependency), and calls `update-desktop-database` best-effort. Only triggered via explicit user action: Settings' "Desktop Integration" row, or the one-time dismissible `DesktopIntegrationNotice` banner on Home — never installed silently. Also calls `app.setName('1.6X Launcher')` (previously unset) so the taskbar/dock name isn't whatever Electron infers by default either. Pending: user retest after this fix to confirm click-to-focus actually works once the entry is installed; if it still doesn't, the next step is an in-app recent-notifications list as a further honest-degradation fallback (not yet built).

  - **Self-review follow-up (2026-08), two real bugs found and fixed before this milestone shipped, both requested by the user as a pre-push review pass rather than found in normal use:**
    - **`playGame`/`connectToServer` silently fell through to `steam://` for a *broken* manual override, not just a missing one.** Both used to check only `install.source === 'manual'`; once an override stops validating, `getActiveInstall` reports `source: null` regardless of whether that's because nothing was ever configured or because a configured override just broke — the two cases were indistinguishable at the call site, so a broken override quietly routed through Steam instead of erroring.     - **An unhandled `spawn()` failure could crash the entire Electron main process, not just fail the launch.** `child_process.spawn()` never throws synchronously for a launch failure (bad binary, permission denied, or the file disappearing in the tiny window between `resolveEngineBinary`'s check and the actual exec) — it always emits an async `'error'` event instead, and Node's documented behavior for an `EventEmitter`'s `'error'` event with no listener attached is to throw and crash the process. The original `spawnDirect` called `spawn()` then `child.unref()` immediately with no error listener at all. Fixed by racing `'error'` against `'spawn'` in a `Promise` (resolves once the OS confirms the process actually started, at which point it's safe to `unref()`; rejects with the real error otherwise) — this both prevents the crash and turns a real launch failure into an ordinary rejected promise the renderer's existing toast handling already knows what to do with. **Confirmed this would have been a real crash, not a theoretical one:** temporarily reverted the fix and re-ran the verify script against a file that exists but isn't executable (passes `validateInstallPath`'s `existsSync` check, fails at actual exec — the exact real-world race this fixes) — the check failed as expected, and the whole Electron process was then killed by SIGTERM moments later from the unhandled event, before the script could even finish. Re-verified clean after restoring the fix.
    - Also added, lower-severity: Settings' and Home's install-status reads now re-check every 30s while the page is open (same pattern `CondebugNotice`/`LaunchOptionsNotice`/`CrosshairWindowedNotice` already use) rather than only once on mount, so a mid-session drive-unmount or folder-rename is reflected without navigating away and back. This is UI freshness, not a correctness fix — every actual write/launch path already re-resolves `getActiveInstall()` fresh on its own regardless of what the UI last displayed, so a stale display was never able to cause a wrong *action*, only a stale-looking button state.
    - Both fixes are covered in `scripts/verify-game-install.mts`'s `resolveLaunchAction`/`spawnDirect error handling` sections. **Still not verifiable without a real environment** (explicitly asked about, not overlooked): the actual UX of a mid-session drive unmount while the game is *running* (session-watcher's qconsole.log tail, the crosshair overlay's poll loop) — this sandbox can't simulate a real block device disappearing under an open file handle, only a path becoming unresolvable *before* an operation starts, which is what's tested. Also unverified: real Windows behavior for any of this (`hl.exe` spawn/error semantics, permission-bit semantics don't carry over from the executable-bit test above) — flagged per the existing Windows-readiness convention (see M15's Windows readiness check note), not yet retested on an actual Windows machine.
